# CODEX-AV — ci: resolve pnpm version conflict

## Brief

> The `Node` CI job has been failing for at least 5 consecutive pushes at the `pnpm/action-setup@v4` step because pnpm is specified in two places: `version: 9` in the workflow's action config and `packageManager: "pnpm@9.0.0"` in the root `package.json`. The action refuses to pick one and exits. Remove the `version: 9` from the workflow so `pnpm/action-setup@v4` reads from `packageManager` (the modern convention). One-line workflow change.

### Goal

`pnpm/action-setup@v4` resolves pnpm to `9.0.0` (from `package.json`'s `packageManager` field) and the `Node` CI job proceeds past the setup step. The Node job goes green for the first time in 5+ pushes (assuming there are no other downstream issues — see "Out of scope" below).

### Context to read first

- `.github/workflows/ci.yml` — the workflow file. Failing step is the `node` job's `pnpm/action-setup@v4` invocation, currently configured with `version: 9`.
- Root `package.json` — already declares `"packageManager": "pnpm@9.0.0"`. This is the source of truth modern Corepack and `pnpm/action-setup` honor.
- `pnpm/action-setup@v4` docs: https://github.com/pnpm/action-setup — confirms that when `version` is omitted and `packageManager` is set in `package.json`, the action reads from `packageManager`.
- Last failure log (one-liner): `Multiple versions of pnpm specified: - version 9 in the GitHub Action config with the key "version" - version pnpm@9.0.0 in the package.json with the key "packageManager"`.

### Files to create / modify

- **Modify** `.github/workflows/ci.yml` — in the `node` job, remove the `with: version: 9` block from the `pnpm/action-setup@v4` step:

  ```yaml
  # before:
  - uses: pnpm/action-setup@v4
    with:
      version: 9

  # after:
  - uses: pnpm/action-setup@v4
  ```

### Behavior

`pnpm/action-setup@v4` reads `packageManager: "pnpm@9.0.0"` from `package.json` at the repo root and installs pnpm `9.0.0`. The `pnpm install --frozen-lockfile` step that follows uses that pnpm version. No other workflow changes; no `package.json` changes.

### Test requirements

The verification IS the CI run. After the change:

1. Push to `main`.
2. The `node` job's `pnpm/action-setup@v4` step completes; `pnpm install --frozen-lockfile` proceeds.
3. Whatever passes or fails downstream of that step is now a real signal, not a setup-step blocker.

Document the run url in the Codex log.

### Acceptance criteria

- [ ] `pnpm/action-setup@v4` step in `.github/workflows/ci.yml` no longer specifies `version:`.
- [ ] `package.json`'s `packageManager: "pnpm@9.0.0"` is unchanged.
- [ ] The `node` CI job on the resulting push reaches at least the `pnpm -r --if-present typecheck` step (passes or fails on real findings, not at the setup step).
- [ ] Codex log notes whether any downstream `node` steps fail; if so, those are flagged as separate follow-up work, not part of AV.

### Out of scope

- Bumping pnpm to a newer version. Keep `9.0.0` — the lockfile and per-package `node_modules` resolutions assume that version.
- Touching `package.json`'s `packageManager` field. Source of truth stays there.
- Fixing any *downstream* typecheck/lint/test failures that surface after setup starts working. Those are real findings; open separate follow-ups.
- The `Rust` CI job (covered by CODEX-AU) and the `validate-agent-files` job (already green).

### Risks / gotchas

- **`packageManager` field must stay present and pinned.** If someone removes it later thinking the workflow handles versioning, the action will fail to determine which pnpm to install. Add a one-line comment in `package.json` near `packageManager`? **No** — JSON doesn't support comments and adding one breaks parsers. Instead, mention this in the Codex log as a known operational consideration, and the agent note pattern can capture it if it bites again.
- **Corepack interaction.** Node 20+ uses Corepack which reads `packageManager` too. If a contributor uses Corepack locally, they get the same version. No conflict.
- **Lockfile version.** `pnpm-lock.yaml` is generated by a specific pnpm version. Don't change the pnpm major; minor/patch changes within v9 should be safe.
- **The other Node-deprecation warning in the CI run** (`Node.js 20 actions are deprecated`) is a future concern from GitHub Actions itself, not the same root cause. Don't try to address that in AV; it's a separate `actions/checkout@v5` + `pnpm/action-setup@v5` (when available) bump. Out of scope.
- **Sanity-check the pnpm version after the install step.** Add `- run: pnpm --version` after the setup step for one CI run to confirm `9.0.0`; remove the diagnostic line once verified, or leave it as a 1-second sanity step (acceptable; document the choice in the Codex log).
